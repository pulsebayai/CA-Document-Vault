## Stack
- **Next.js (App Router) + TypeScript** — one codebase for UI and server actions/API routes.
- **Supabase (Postgres + Auth + Storage), region ap-south-1 (Mumbai)** — relational data, row-level security, private file storage in India.
- **Vercel, functions pinned to bom1 (Mumbai)** — preview deploys per PR; no document bytes cached (private bucket, short-lived signed URLs).
- **Email = Brevo (Raja 2026-10-01; replaces AWS SES)** — **staging and prod move to AWS SES Mumbai (2026-11-06, decision log; dev stays on Brevo):** one provider for staff sign-in codes/invites (Supabase Auth custom SMTP) **and** client reminder emails (sent by the app through one mailer interface; CI/tests use a transport that never sends). **One Brevo account per environment** (dev today; a separate account for staging/prod). Production: a **paid plan** (the free plan's 300/day cap is shared with sign-in codes and adds Brevo branding), the **firm's domain authenticated** in Brevo (DKIM/DMARC), Reply-To = **the staff member who sends** (06 decision 1), a per-client and per-day reminder cap so reminders can never starve sign-in.
- **Sender (17):** one platform From address (`MAIL_FROM_EMAIL`, one verified domain for every firm) with the **sending firm's name** as the display name (`sendMail(message, cfg, { fromName })`; CR/LF, quotes and angle brackets removed, ≤ 70 characters); Reply-To stays the staff member. `MAIL_FROM_NAME` ("CA Document Vault") is only the fallback for mail with no firm. The office ceiling `EMAIL_DAILY_MAX` applies to each firm separately (no platform-wide ceiling, owner 2026-11-03).
- **Mailer (06):** one server-only interface `src/lib/mail/` (`sendMail`), transports `brevo` (HTTP API, 10 s timeout), **`ses` (chore ses-mailer: AWS SES v2 `SendEmail` in ap-south-1 only, 10 s timeout, no SDK retries, credentials passed explicitly; dev never uses it)** and `test` (never touches the network; **the default when `MAIL_TRANSPORT` is unset**, so CI, local runs and previews never send). Inside `send`, before any transport: an address ending `.test` is never sent; outside production (`APP_ENV` ≠ `production`) only `EMAIL_ALLOWLIST` addresses are. `BREVO_API_KEY` is readable only in `src/lib/mail/brevo.ts`, and `SES_ACCESS_KEY_ID` / `SES_SECRET_ACCESS_KEY` / `SES_REGION` only in `src/lib/mail/ses.ts` (ESLint fences, like `SUPABASE_SECRET_KEY`; `SES_*`, not `AWS_*`, which Vercel reserves). Staging and prod set `MAIL_TRANSPORT=ses` explicitly (R1 checklist); `LINK_IP_SALT` is then required, as for `brevo`.
- **Storage sweep (10):** `/api/cron/storage-sweep`, run daily by **Vercel Cron** (`vercel.json`, 19:30 UTC), removes stored files that no `document_version` points at and that are older than 24 hours (03's failed saves and 10's unregistered link uploads), listed by `orphan_objects()` (service role) and deleted through the Storage API (Supabase refuses SQL deletes on `storage.objects`). The route checks `Authorization: Bearer <CRON_SECRET>` (server env var, ≥ 16 chars, per environment; unset = 401, nothing removed) and is public only as that exact path.
- **Scheduled jobs:** Supabase pg_cron. `expected-docs-daily` (18:45 UTC = 00:15 IST) runs `private.run_office_expected` for every non-test office: next FY from 1 February, generation, back-link, one `expected.generated` activity row (actor = system). This is the first writer with no signed-in user: definer, tenant-scoped per office (04). The extension and job must exist on staging/prod (R1 checklist). 10 adds `link-attempts-daily` (19:00 UTC): `link_attempt` rows older than 7 days are deleted (hashed IPs; throttle evidence only).
- Tailwind · Vitest + React Testing Library · Playwright · ESLint · GitHub Actions.

## Core entities — dimensional document model
Reference: sdlc/product/references/data-model-v3.md. **No folder hierarchy.** A document is one file + one metadata row; every "folder" view (by client, group, type, FY, period) is a query.

**Five dimensions (master tables; documents store IDs, never free text):** client, doc_group, doc_type, financial_year, period. GSTIN/TAN is an optional *attribute* (`registration_id`), not a dimension.
- `client` (code, name, type, PAN, email, mobile, incharge → staff_user, archived) · `client_registration` (GSTIN/TAN…, state; 1..n) · `client_contact` (reference only)
- `doc_group` (GST, TDS/TCS, Income Tax, Banking, ROC/MCA, Payroll, Audit, Accounting, Registrations, Other; sort, active)
- `doc_type` (→ doc_group, code, name, default frequency, period_kind month|quarter|year|none, status approved|proposed, proposed_by)
  - **Schedule = offsets from period end** (`ask_after_months, ask_day, overdue_after_months, overdue_day`): one rule for monthly, quarterly and yearly collection (02).
  - `source client|firm`: the catalogue is what the firm needs *from the client*; **firm records** (returns filed, acknowledgements) are `firm` — no schedule, never copied into a plan (02).
  - `aliases text[]` (old/new form names, e.g. Form 16 ↔ Form 130) · `registration_kind gstin|tan|null`: collected per registration (04 generates one expected doc per active GSTIN/TAN) (02).
- `client.code` is vault-generated (`C0001…`, per-office counter, never reused); `previous_reference` holds the firm's old code. PAN unique among non-archived clients; once a GSTIN with that PAN exists the PAN is fixed (archive + re-add) (02).
- `financial_year` (code 2026-27, start, end)
- `period` (kind month|quarter|year, code, start, end, → financial_year) — generated, never typed

**Document (the fact row)**
- `document` (DOC-ID, client_id, doc_type_id, period_id NULL-able for undated docs e.g. registration certificate, registration_id NULL-able, expected_doc_id NULL-able (04), received_as soft copy|hard copy|original, channel WhatsApp|Email|Hand delivery|Courier|Portal download|Other, received_by/on, status, remark, classified_at, archived) → `document_version` (append-only: storage path, sanitised file name, type, size, uploader; the newest is current, same DOC-ID) (03)
  - **DOC-ID = `DOC-FY26-27-00001`**: per-office counter (`doc_counter`) per FY of the date the document is **added** (IST), restarts 1 April, no gaps, never reused or edited (03).
  - **Classified** = client + type; otherwise the document is in the **Inbox**. `classified_at` is set once (metric 4) (03).
- **Review & dispatch (07):**
  - **Review state** lives on the document (`status` received = To review · reviewed · needs_correction; `reviewed_by/at`, `correction_reason`) for fast lists. An **append-only `document_review`** keeps the history (reviewed · needs_correction · undone · reset, with reasons). This is the "free text lives on the entity, never in activity" rule, extended to text that changes over time.
  - **Status gate:** `document.status` changes only inside `review_document` / `undo_review` (transaction flag `app.doc_review` = the document's ID). 03's trigger **resets** a review to To review on a new version or a client/type/period/registration change (with a `reset` history row; the save's activity row gets `review_reset`). A corrected file for a Needs-correction document may replace received on.
  - **Dispatch = packets per client** (`dispatch` + `dispatch_item`): date, method, optional courier and tracking, a required recipient. All-or-nothing. **One live packet per original** (unique index on live items). Undo (Admin/Manager) removes one item with a reason; nothing is deleted.
  - A dispatched original can't change client or received-as until its dispatch is undone. A corrected file for a dispatched original is a new version of that document; the dispatch stays (Raja, PR #25 Q3).
  - **Review and dispatch are separate dimensions:** a Needs-correction original can be dispatched, and still counts as not received.
  - **Shown state** is derived in one TS function (`src/lib/documents/state.ts`, order: Archived · In inbox (shown "Untagged", 12) · Dispatched · Ready to dispatch · Needs correction · Reviewed · To review). Tested equal to the SQL `return_state` used by search. **13:** Ready to dispatch is now a stored custody step and "Document in office" sits between Needs correction and Reviewed (see 13 below).
- **Intake & review fixes (12, Kushal review 2026-10-29):**
  - **Returnable hard copy replaces "original"** (supersedes the 2026-09-28 received-as row). `received_as` is the paper form only (soft copy · hard copy); `document.returnable` (true only on a hard copy, check constraint) is the return obligation. Everything 07 keyed on "original" now keys on returnable: Ready to dispatch, `create_dispatch` eligibility, Today, the `/documents` Return filter and state, the document page's Dispatch panel, and the dispatch lock (a document in a live packet can't change client, received as or Returnable).
    - The enum value `original` stays but is refused as a stored value (`document_not_original`). **Legacy input rule:** `original` in any write is stored as hard copy + returnable (the trigger maps it on every path, so older callers, test helpers and `?as=original` links keep working); `received_as` sent without `returnable` keeps its old meaning.
    - Migration A converted 136 originals on dev; on staging/prod the counts are recorded at the replay. Pattern for a data step that touches archived documents: disable `document_before_write` for that one statement, then `set constraints all immediate` before re-enabling (03's deferred soft-copy check queues events).
  - **Handed over by** = `document.handed_over_name` (one text field, D1; 1–120; hard copies only; can be changed, not cleared). The database checks the shape only; the server actions require it for a new hard copy or a change to hard copy (older hard copies stay editable without it). Personal data: on the entity only (06's PII-snapshot rule), never in activity (activity records only that the field changed), URLs or logs.
  - **Correction kind:** `document.correction_kind` and `document_review.correction_kind` (`file` | `details`), set by `review_document(…, p_kind)`. The dialog requires it; the server accepts a call without it (07's callers). **Reset rule (AC-23, plan R1):** every Needs-correction or Reviewed document keeps 07's rule (a new version, or a client/type/period/registration change, sends it back to To review). A *wrong details* correction also resets on a change of received as, Returnable, received on or handed over by. Remark, channel and received-by never reset a document.
  - **Undo review = Staff, Manager, Admin** (Limited refused); undo dispatch stays Admin/Manager. Two permission-matrix rows ("Undo a review" · "Undo a dispatch"), each probed per role.
  - **Lists:** `/documents` passes `page_size: 20` (the SQL default and cap stay 50 for other callers); Client › Documents pages each card by 20, newest received first, in the browser. View / Download on Untagged, `/documents` and Today rows come from one RLS lookup per page (`currentFiles`, batches of 100, best effort), not from the search or Today functions.
  - **"Inbox" is named "Untagged documents"** on screen (D2); the route `/inbox`, the `inbox` state value and code names are unchanged.
  - **My clients:** `search_clients(…, p_mine)` narrows the Clients list to clients whose incharge, or the assigned staff of an active group or plan row, is the user (06's effective assignee). A filter, never access. On by default for Staff, off for Admin/Manager, absent for Limited; a URL flag (`?mine=1|0`, no PII) — the one Clients-list filter in the URL.
  - **Type field:** matching is pure TS in the browser (`src/lib/types/match.ts`) over the types the form already loads (plan types + approved types, with aliases); ≈ 1.6 ms for 500 types.
- **Hard-copy custody (13, Kushal review Q3, Q8; Sankar #6, #14):**
  - **Custody is a stored dimension beside review and dispatch** (supersedes 07's derived Ready to dispatch): `document.custody` (`in_office` | `ready` | null = not placed) + `in_office_at/by`, `ready_at/by`; history in the append-only `document_custody` (`in_office` · `ready` · `undo_in_office` · `undo_ready`, `implied`, actor, at). Columns change only inside `set_custody` / `undo_custody` / `create_dispatch` (transaction flag `app.doc_custody` = the document's ID; the gate is in 03's `document_before_write`), or the service-role backfill (`'backfill'`).
  - **Steps:** a filed hard copy with a review decision (Reviewed **or Needs correction**, S1) → In office → (returnable only) Ready → 07's packet. Every role moves and undoes (Limited on clients they can see); undo needs no reason (S3) and is refused while in a live packet. A review reset keeps custody (Q4). While in custody a document can't become a soft copy; while Ready it stays returnable (S5).
  - **Shown state** (`state.ts`, SQL `private.custody_state`, tested equal): Archived · Untagged · Dispatched · Ready to dispatch (stored Ready + review decision) · Needs correction · **Document in office** · Reviewed · To review. Search's `return` filter keeps its key; values `to_place · in_office · ready · dispatched`, plus `held`.
  - **S2, a legacy-input exception:** `create_dispatch` still accepts a reviewed returnable copy nobody marked Ready and records the skipped steps as **implied** (by the dispatcher). The screens offer dispatch only for stored Ready. Undo dispatch leaves the document Ready.
  - **Held** = returnable, in custody, not in a live packet, marked in office more than 30 office days ago (`private.custody_held`; one office-wide number). Shown as "In office N days" only past 30 (07's "Held N days" from received on is unchanged, P1).
  - **Today:** `today_items` counts `to_place` and `held`; their rows come only with `p_show = 'to_place' | 'held'` (the default list stays To review + Ready). `ready` counts stored Ready.
  - **Log receipt** = `log_receipt(p)` (invoker): N hard copies with no file through 03's unchanged `create_document`, one transaction (one filing path). Untagged when no type is given. The paper reference is client code + DOC-ID (no second ID).
  - **Data step:** `public.custody_backfill(office)` (service role, idempotent; also run by tests on their own office): live packet or returnable with a review decision → Ready; other reviewed hard copies → In office; dates = `reviewed_at`, who = null. Dev: 125 Ready + 561 In office. Staging/prod: counts recorded at the replay.
  - **Metric:** `custody_metric(from, to)` (Admin/Manager) on Settings › Collection: placed within 2 working days (non-implied, migrated rows excluded), median Ready → dispatched, held now.
- **Derived, not stored:** doc_group (from doc_type) and FY (from period). Prevents "type in GST, group = Banking" inconsistencies and makes admin re-mapping of types safe.
- **Search (03b)** = `search_documents` + `search_document_facets` (SECURITY INVOKER, one jsonb argument from a server action): filters on any combination of dimensions; facets (group, received as, channel, received by, status) counting the visible matches with every filter except their own; text = up to 5 words, each matching (case-insensitive, partial, `\ % _` escaped) the remark or current file name, or prefixing the DOC-ID. No full-text/pg_trgm and no search indexes yet: both wait for the volume test (roadmap "Before pilot"). The word rules are written out in both SQL functions and in `normaliseSearchText`; change all three together.

**Expectation layer (= "collection requirement" in reference doc)**
- **Master templates → client instances.** Master = `doc_group` + its `doc_type`s with default schedule (frequency, ask day, overdue day, reminders on/off). When a group is enabled for a client, its types are **copied** into `client_doc_type` rows (client × doc_type: frequency, schedule, reminders, assigned staff, active/paused, start period). The copy keeps `doc_type_id`, so the dimension stays shared for search, but the schedule is the client's own.
  - Later master edits do **not** silently change existing clients; admin can explicitly "apply to existing clients" (logged).
  - Staff+ (not Limited) can add a type to one client only (proposed type, after the closest existing types are suggested) — it becomes a `client_doc_type` immediately (as needed, no reminders); if the group isn't enabled for that client, a client group row is created holding only that type. Proposed names are unique per group per client (05 merges) (03).
  - `client_doc_type` rows *are* the client's collection plan; `expected_doc` rows are generated from them.
- `expected_doc` (client × doc_type × period [× registration]; ask/overdue dates; status pending|received|waived) — **unit of metric 1**. 1 expected_doc : n documents (e.g. many invoice PDFs for one month). (04)
  - **Exists from its ask date** (period end + offsets, IST); no stored "upcoming" items. Generated for active, scheduled, client-source, approved plan rows from the row's start period; one per active GSTIN/TAN for per-registration types (none without one). Unique (plan row, period, registration).
  - **Shown state is derived, never stored:** Due · Due today · Overdue · On hold (row or group paused) · Received · Not needed. One TS mirror (`src/lib/expected/schedule.ts`) is tested equal to the SQL dates for every generated item.
  - **Plan changes act in DB triggers** on `client_doc_type`, `client_group`, `client_registration` and `client` (definer, tenant-first): immediate generation; pending-only date recompute; auto-waive with a system code (removed from plan · registration inactive · before start). Re-enabling restores not-yet-overdue "removed" items; resume (`resumed_on`) skips periods that fell overdue while paused.
  - **Default start period = the earliest still-open period** of the row's frequency (changes 02's "current period").
  - **Linking:** an AFTER trigger on `document` maintains `document.expected_doc_id` and the item's status / received on. **Counts as received (07)** = linked, not archived, **and not Needs correction**. A second AFTER trigger (`document_after_review_link`, WHEN the status changed) recomputes on review changes, including resets made inside 03's BEFORE trigger, at no cost to ordinary saves. A document with no GSTIN/TAN for a per-registration type links only when the client has exactly one active registration of that kind.
  - **Staff actions:** Waive (Staff+, reason) · Undo (Admin/Manager) · Reopen (anyone who sees the client): invoker functions. Only functions write `expected_doc` (no app write policies).
  - **Metric 1** = received before the overdue date ÷ items whose overdue date passed (waived, on-hold and archived-client items excluded): `collection_metric`, shown on Settings › Collection (Admin/Manager).
- **Today = derived view (06):** `today_items(scope, show, page)`, one SECURITY INVOKER call: pending items, not on hold, overdue or overdue within 7 days (office date), cards per client. **Effective assignee** = plan row's staff → its group's staff → the client's incharge (the same columns as `can_see_client`) defines "Mine". Not stored.

**Upload requests (10; direction approved 2026-10-25, details in 10's spec)**
- `upload_request` (client, token hash, expiry, revoked, caps, created_by, sent via email|whatsapp) → `upload_request_item`, one or more per request, of two kinds:
  - **scheduled** → a pending `expected_doc`;
  - **ad-hoc** → doc_type (required: approved, as-needed or proposed), optional period, optional needed-by date, public note ≤ 200 chars, status.
- **Ad-hoc items are not expected docs.** They never create `expected_doc` rows and never count in metric 1, and they never appear in the Clients list counts or "Has overdue".
- An open ad-hoc item shows on Client › Requested and on **Today of the staff member who created the request**. This is a deliberate exception to 06's effective assignee: the person who asked chases it. It is overdue after its needed-by date.
- An upload creates a classified `document` via 03's path. Client, type and period [+ registration] come from the item. The document is received at once and flagged for mandatory staff review ("from client link"). Scheduled items link through 04's trigger.
- **Built (10a):**
  - `upload_request` keeps `token_hash` (SHA-256 hex; excluded from the column grant), `expires_at` (sent day + 14 office days, midnight IST), revoke fields, `replaced_by`, `follow_up_id`, caps `max_files` 30 / `max_bytes` 300 MB and counters. RLS: select iff `can_see_client`; writes only inside 10's functions (`app.upload_write`, guard trigger `private.upload_change_guard`); delete only by the test purge.
  - **Link uploads are owned by the requester (P1):** `link_register` calls 03's **unchanged** `create_document` with the request creator's identity: one helper (`private.link_act_as`) sets the JWT claims transaction-locally, so `auth.uid()` and the staff/office helpers return the requester. It is refused when the requester is inactive or can no longer see the client. 03's DOC-ID, versions, review reset and 04's linking all apply as for a staff upload. Channel `upload_link`, received as soft copy. The `document.link_upload` activity row has **actor null** (the client did it) and IDs only.
    - **RLS does not apply on this path.** Called from the definer `link_register`, the invoker `create_document` runs as the function owner, so table policies are skipped. The authorisation is the explicit checks in `link_request` / `link_item` (office, link state, `can_see_client`, item on the link) plus 03's triggers. A rule added later only as an RLS policy will **not** cover link uploads; add it to those checks too.
    - The stored file name always ends in the stored object's extension, whatever the browser sends (`invoice.exe` → `invoice.pdf`).
    - **Channel `upload_link` is set only by `link_register` (`app.link_register`) and never changes** (`document_channel_guard`), so the badge and download-only rule can't be edited away. The Edit form shows it read-only.
  - `document.upload_request_item_id` links the document to its item. **Ad-hoc item status** (open → received) is kept by its own document triggers (`private.recompute_request_item`), mirroring 07's "counts as received" (not archived, not Needs correction) and 04's reopen rule (`reopened_at`).
  - The requester gets one bell notification (`notification_kind.link_upload`) per link per office day (D6).
- **Built (10b):**
  - **Client › Requested** lists the client's ad-hoc items and links (RLS reads). **Send again** moves the old request's open ad-hoc items to the new request (item kind `carry`; same item ID, documents stay linked) and revokes the old link in the same call; it follows the revoke rule (own link, or Admin/Manager).
  - **Staff "Upload" for an item** = `create_document_for_item(p_item, p)` (invoker): 03's unchanged `create_document` + a definer helper that sets `document.upload_request_item_id` + an `upload_request_item.filed` activity row, one transaction. Client and type come from the item. The document keeps the channel staff chose.
  - **Today:** `today_items` returns requested rows (`kind: 'requested'`, `due` overdue | due_week) on the requester's Mine and on Everyone, `counts.requested` (all open) and `counts.requested_later` (not shown as rows, D7), `p_show = 'requested'`. 06's expected counts stay expected-only. A link upload To review is also on its requester's Mine.
  - **Metrics:** `link_metric(from, to)` (Admin/Manager) on Settings › Collection; metric 1 (`collection_metric`) never sees ad-hoc items.

**Preferred file formats (11; advisory, never enforced)**
- `doc_type.preferred_formats text[]` (null = no preference): a distinct, non-empty subset of the upload allow-list **minus ZIP** (`pdf jpg png heic xlsx xls csv docx`), set only on approved types (check constraint built from built-ins only, so service-role writes work; Admin/Manager through the catalogue). Pre-loaded once for six types on the real office (migration A); automated-test offices start with none and tests switch them on with `test_seed_preferred_formats` (service role, `is_test` only), so 02's `seed_catalogue` is unchanged.
- **Exception per client + type:** `client_doc_type.any_format boolean`. Staff/Manager/Admin by the existing `client_doc_type` RLS plus a column grant; Limited can't (P1). Logged as `client_doc_type.format_exception_set` / `_cleared`.
- **Format check snapshot on `document`:** `format_preferred text[]` (the preference that applied, or null) and `format_ok bool` (null when none applied). Set in 03's `document_before_write` **only** when the client or type changes or the current version changes (create, new version, re-classify); kept on review, archive, 05's merge (`app.type_merge`) and later preference or exception changes, so history is never rewritten and the metric has a fixed denominator. The format is the stored object's extension (`jpeg` → `jpg`). Because it runs in the trigger, it covers 10's link path too, where RLS doesn't apply.
- **Nothing is ever refused for its format** (no server path checks it). Staff see a warning in the document form and Add version; the client's `/u` page shows "X preferred" and a warning with "Choose another file" / "Upload anyway" (`link_open` returns `preferred`, absent when the client has an exception, and never says why). The page's answer travels as `warned` to `link_register`, which writes `data.warned: true` on 10's `document.link_upload` row **only when true** (untrusted; metric only).
- **One format rule in three places**, tested equal: `src/lib/validation/formats.ts` (labels, `isPreferred`), SQL helpers `public.format_label` / `format_of_path` (service role only) and `private.format_check` (used by the trigger) — the same pattern as 03b's search words and 04's schedule mirror.
- **Reads:** 03b's `search_documents` / `search_document_facets` (replaced, same signature) take `format = 'not_preferred'` and return a `format` facet (hidden at 0) plus `format_ok` / `format_preferred` per row; the badge "Not preferred format" shows on Client › Documents, `/documents` and the document page. **Not** on Today (P2, `today_items` unchanged) or in the Inbox (P3: Inbox documents have no type, so no check).
- **Metric:** `format_metric(from, to)` (invoker, Admin/Manager) on Settings › Collection: share filed in a preferred format (link / staff), warned link uploads that switched vs uploaded anyway, median hours to review a flagged link upload, and exceptions by type (top 5, as of now). Existing documents (before 11) have no check and are never counted.

**Operational**
- `office` = **one row per firm** (17; Kushal Associates first): name, branch, FY start, counters, `is_test`, test clock; 19 adds `suspended_at` / `suspended_by` / `suspend_reason` (written only by the platform functions; no grant to staff). ## Auth & permissions model
- **Staff only sign in.** Admin creates/invites each staff user; no self sign-up. **One email = one firm (17):** `staff_user.id` = the auth user and `email` is unique across firms; a person who works for two firms uses two addresses. Inviting an address in use anywhere is refused with a message that names no firm ("This email is already in use. Use a different address."); that the invite fails is the accepted residue. The first Admin of a firm comes from the bootstrap. **Operator access (17, refined by 19):** the platform operator reaches a firm's data only through the super admin console (19) or the operator scripts, every action logged, never through a staff account in a customer's office. Sign-in by **email one-time code** (Supabase Auth OTP). Deactivating a user revokes access immediately.
- **Super admins (19):** Pulsebay's platform operators, **outside every firm**.
  - **Identity:** `platform_admin` (id = the auth user, email, name, status active | deactivated; RLS: a super admin reads only their own row; no app writes). Added, deactivated and reactivated only by the operator script `scripts/add-platform-admin.mjs` (service role, dry run unless `--yes`, `--yes-production` on prod, `.test` only with `--test`; never deletes). **An email is either staff in one firm or a super admin**: a trigger pair (`private.platform_email_clash`) refuses a clash both ways (`EMAIL_IN_USE`), and 17's neutral invite message stays. A `.test` super admin acts on test offices only, a real one on real offices only, so fixtures can never reach a real firm.
  - **Sign-in = the staff email code, no second factor in R1** (accepted risk, decision log). `finishSignIn` returns one access state (`src/lib/auth/access.ts`: staff · platform · suspended · none) used by sign-in and by `requireStaff`'s refusal path (`public.my_access_state()`, asked only when the staff row is missing). A super admin lands on `/platform` and is sent there from every staff page; anyone else gets Not Found on `/platform` (`requirePlatformAdmin` = `platform_whoami()`). A super admin's sign-in is written to the platform audit and **fails closed** if it can't be.
  - **Every platform action is a SECURITY DEFINER `public.platform_*` function** that starts with `private.require_platform_admin()`, works on the firm passed explicitly (`private.platform_office`, test ↔ real), and **writes its platform audit row before returning** — every action and every read of firm data. Four reads of platform metadata are not logged: `platform_whoami` (the caller), `platform_firms` (counts only), `platform_invite_target` (the waiting first Admin's name and ID, no email) and `platform_audit_list` (the log itself). `require_platform_admin` also requires the sign-in email to still be the one on record (a changed login email loses platform access). Executable by `authenticated`, refused (`NOT_PLATFORM_ADMIN`) for everyone but an active super admin. They return IDs, counts and display fields, never storage paths, `password_ct` or token hashes. `platform_create_firm` runs 17's unchanged `bootstrap_office` with the JWT claims cleared for that call (02's tenant-first triggers apply to any caller with a JWT, and a super admin has no office). **The one service-role step is the first Admin's invite email** (`src/lib/platform/invite.ts`, ESLint allow-list): it first asks `platform_whoami()` as the signed-in user, reads the firm's name and staff count back from `platform_firms` (never the browser), and the staff row is then written by `platform_record_first_admin` as the user; a resend is logged by `platform_begin_reinvite` (as the user) before it is sent, and only an account the call created is ever removed. The sign-in audit is `platform_signed_in` (as the user). The only other service-role reads on platform tables are 01's sign-in lookups (`auth/actions.ts` — may this address get a code; the staff invite's one-email check), never a write. Suspend and create are refused in a one-firm (single) deployment (`SINGLE_MODE`); a real super admin can't create a firm before the deployment mode is set or name one "e2e office …".
  - **Support access = reason (10–500) + a 60-minute window per (super admin, firm)** (`platform_access`; open / close, no policies). The six read views (`platform_clients`, `_client`, `_documents`, `_document`, `_expected`, `_activity`) need an open, unexpired window for that firm and write a platform audit row **and** a firm activity row `platform.viewed` (IDs + view name: `client_id`, or `document_id` + its client) before returning. **Read-only, PII shown in full; no file download and no DSC reveal** (no function returns them). Opening writes `platform.access_opened` (access ID only; the reason stays on the access row) and one bell notification (`platform_access`) to each active Admin. The firm sees these as "Pulsebay support …" sentences (the catalogue's per-action actor) under the **Support access** Activity filter, on the client's and the document's own activity (15's `document_id` lookup), and Limited users see views of clients they can see.
  - **Suspension lives in the three staff helpers:** `current_staff_id()`, `current_office_id()` and `has_role()` join `office` and return nothing while `suspended_at` is set, so every RLS policy refuses the firm's staff on their next request with no policy change (`clients-list` +0.4 %, K4 within noise). 10's links answer `NOT_ACTIVE` (`link_request` acts as the requester), 04's nightly job skips suspended offices (`test_platform_probe()`, service role, rolled back). Staff see "This firm's access is paused" (`/auth/paused` signs out, then `/login?reason=paused`); nothing is deleted. `office.suspended` / `office.reactivated` firm activity rows (actor null, no reason).
  - **`platform_audit` is append-only** (`private.forbid_change` per row and a TRUNCATE guard, service role included), `detail` = IDs and view names only (`private.platform_audit_no_pii`); free text lives on its own row (the access reason on `platform_access`, a suspension's reason in `platform_audit.reason`, which reactivation can't clear). Read through `platform_audit_list` (Platform › Audit). Operator script changes are logged with `admin_id` = the super admin they are about.
  - Search text typed in the console goes by POST (server action), never into a URL.
- **Client upload links (10):** the one route outside staff auth.
  - The bearer token in the link is ≥ 128-bit random, stored hashed and never logged. There is no client login and no one-time code (Raja + Kushal 2026-10-25).
  - The page is upload-only. It shows the firm name, item names, ad-hoc notes, needed-by dates and masked registration labels, and never existing documents, PAN, full GSTIN or contact details.
  - An upload is accepted only for an item on that link, before expiry, unrevoked, within caps and rate limits.
  - Writes go through a dedicated definer path that checks the token, tenant and item first. Storage stays policy-less for app roles (signed upload URL, as in 03).
  - Building or sending a request uses the same roles as Remind. Limited users can do it only for clients they can see.
  - **Public route pattern (10a; reuse it for any future public route):**
    - The token travels in the URL **fragment** (`/u#<43-char base64url>`), which browsers never send to a server, so it can't reach Vercel or proxy logs. The page POSTs it in the body of a server action. The route sends `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex` and `Cache-Control: no-store`.
    - The database functions (`link_open`, `link_ticket`, `link_register`) are SECURITY DEFINER and executable **by service_role only**. They are called only from the server-only module `src/lib/upload-links/public.ts` (on the ESLint service-role allow-list). Anon and authenticated can't call them.
    - The check order is fixed: IP throttle → token → office → link state (expired, revoked, replaced) → item on this link → file rules → caps → per-link throttle.
    - **Every unusable link gets the same answer** (`NOT_ACTIVE`), so a caller can't tell a wrong token from an expired one.
    - Throttling uses `link_attempt` (`ip_hash` = SHA-256 of the IP with the server secret `LINK_IP_SALT`, never the raw IP). It allows 20 failed lookups per IP per 10 minutes (counted by all three functions: an unusable link is *returned* as `{error: NOT_ACTIVE}`, not raised, so the log row commits) and 60 upload tickets per link per hour. The table has no policies and no `office_id` for unknown tokens (no office is known). Rows are kept 7 days (`link-attempts-daily`).
    - Caps are checked under a row lock on `upload_request`. Tickets are capped for the link's lifetime at 2 × `max_files` (`tickets_count`), which bounds unregistered objects per link; the daily storage sweep removes them after 24 hours.
    - `LINK_IP_SALT` is required (the server refuses to start a link action without it) on prod, on any Vercel production deployment and whenever `MAIL_TRANSPORT=brevo`.
    - `/u` is public as exactly `/u`; any future `/u/*` route needs staff sign-in unless added deliberately.
    - Errors returned to the page are codes only. No DOC-ID, client or staff data is returned beyond what the page shows.
  - **Link base URL:** `APP_PUBLIC_URL`. When it's unset on Vercel, the base is `VERCEL_PROJECT_PRODUCTION_URL` (production) or `VERCEL_URL` (preview). Staging and prod set `APP_PUBLIC_URL` and `LINK_IP_SALT` explicitly (R1 checklist).
- **Secrets at rest — application-level encryption (14):** DSC token PINs are encrypted in the server by `src/lib/dsc/crypto.ts` (AES-256-GCM, random 12-byte IV, 16-byte tag pinned with `authTagLength`, AAD `dsc:<keyId>`; stored `k<keyId>.<iv>.<tag>.<ct>`, base64url) with `DSC_ENC_KEYS` (`<id>:<base64 32 bytes>`, comma-separated) / `DSC_KEY_ID`, server env per environment; ESLint fence: only `crypto.ts` reads them. The key never reaches the database or the browser; the database checks only the ciphertext's shape. Fails closed (no key, malformed key, unknown key ID, tampered value) with fixed codes, never the key or the value. The public test key (CI, sessions) is refused whenever `APP_ENV` or `VERCEL_ENV` is production, by ID and by its bytes. Rotation: add a key ID, re-encrypt, remove the old one (manual in R1, `sdlc/releases/README.md`).
  - **Reveal = a definer function that logs before it returns:** `password_ct` is outside the column grant (a `select=*` or an embed fails rather than leaks); `dsc_reveal(id)` (role first, then tenant, `can_see_client`, not archived; Limited never) writes `dsc.password_revealed` and returns the ciphertext in the same transaction (VOLATILE: a read-only call fails at the insert; tested with `Prefer: tx=rollback`). The server decrypts and returns the value in the action's POST response only; the page shows it for 30 s of wall-clock time and overwrites a copied value on the clipboard when it hides. PIN fields are masked text fields with password-manager opt-out attributes, so browsers never store a client's PIN. Activity › "Password reveals" lists every reveal for the weekly check.
- Roles enforced in **Postgres RLS**, not only in UI. Matrix (from mockup): Admin/Manager/Staff see all clients; Limited sees only assigned clients/groups. Manage users → Admin only. Catalogue approvals, incharge changes, pausing → Admin/Manager.
- **Permissions matrix is code (08):** `src/lib/auth/permissions.ts` (28 rows × 4 roles since 17: send upload links, revoke someone else's link (10); allow any format for a client + type (11); undo review · undo dispatch split (12); move a hard copy in office / ready, undo a custody step (13); add and edit DSCs, reveal a DSC password, log DSC custody, archive a DSC (14); edit the firm's name and branch (17)) is the one source for Settings › Users and for `tests/rls/role-matrix.test.ts`, which runs a probe for every row × role against the database. A row without a probe fails the test, so the screen can't drift from what is enforced. New role rules add a row and a probe.
- **Activity visibility (08):** Admin/Manager/Staff read all of the office's activity. **Limited** read a row only when they are its actor or can see its client (`activity_select`).
  - The client comes from `data.client_id`, else from the row's entity (client · document · expected_doc · follow_up · dispatch · client_group · client_doc_type), via `private.activity_client` (definer, tenant first, regex-checked IDs, no exception blocks).
  - Rows with no client (catalogue, users, sign-ins, system jobs) are visible to Limited only as the actor.
  - A document's past events follow its **current** client (IDs only; names stay behind RLS).
  - The feed is `activity_feed(p jsonb)` (SECURITY INVOKER): names are joined under the viewer's RLS; sign-ins appear only on request. Sentences are built in TS (`src/lib/activity-feed/catalogue.ts`); a unit test requires one for every action written in `src/` or the migrations.
  - **Activity of a document (15, K4):** a row belongs to a document when it is about it (`entity_type` 'document', `entity_id`) or its data names it (`data.document_id`, `data.document_ids`). Each kind has its own index (08's `activity_entity_idx`; 15's partial `activity_doc_ref_idx` btree and `activity_doc_ids_idx` GIN), and a document's rows are found by **one indexed lookup per kind, never an OR**. The lookups run in `private.doc_activity_ids(doc)` (SECURITY DEFINER, plpgsql so its plan is cached (Postgres 17 re-plans non-inlined SQL functions per call), the caller's own office, **row IDs only**, newest first); `activity_feed`'s document filter and `document_last_activity` stay invoker and read those IDs back under RLS (`id = any(…)`), so `activity_select` still decides every row returned. Why a definer helper: under RLS the planner applies non-leakproof quals (`->>`, jsonb `?`) only after the policy, so the expression and GIN indexes can't serve them inside an invoker query. Reuse this pattern for any future per-entity activity read. The reference actions are listed in `src/lib/activity-feed/document-refs.ts`; a unit test fails when a migration adds another, so its lookup is checked.
  - **`document_last_activity(p_ids uuid[])`** (invoker, ≤ 50 IDs): the newest visible event per document (sign-ins excluded), one call per page of a list; it walks each document's IDs newest first and stops at the first row RLS lets through.
- "Delete" in the mockup = **archive** (reversible, logged). No hard delete from the app.
- **Assignment decides what Limited users see**, so assigning staff (group or type), changing the incharge, pausing/resuming and switching off a paused group are Admin/Manager only (DB triggers). A group follows the incharge: when the incharge changes, groups still assigned to the old incharge move to the new one (logged) (02).
- Settings is visible to all staff; each item is role-gated (catalogue writes Admin/Manager, users Admin) (02).
- The service role cannot write `client` rows (CHECK helpers are `authenticated`-only); tests and tools create clients as a signed-in user (02).
- **Documents (03):** visible if the user can see the client (`can_see_client`), or unclassified and (Staff+ or added it). Limited users add/edit only for clients they can see or into the Inbox. Archive/unarchive Admin/Manager (reason required); archived documents are read-only.
- **Files (03):** bucket `documents` private (25 MB, MIME allow-list), **no `storage.objects` policies for app roles**. Upload: server issues a signed upload URL for `office/<office>/doc/<document>/<version>.<ext>` (IDs only) → the browser PUTs the raw file with our canonical Content-Type → the DB registers it, **reading size and type from `storage.objects` itself** (the RPCs are callable directly). View/download: a ≤ 60 s signed URL issued server-side after an RLS lookup; only `src/lib/documents/storage.ts` signs (service role, ESLint allow-list).
- **Bulk files (08):** the zip is built **in the browser** (`client-zip`, store-only); no document bytes pass through our servers.
  - The server lists the selection's current files (≤ 100 files / 300 MB of stored sizes; RLS as the user), then signs ≤ 10 links per call just before the browser fetches them. Each link lives ≤ 60 s, comes after 03's RLS lookup, and is signed by `storage.ts`. Storage answers cross-origin GETs with `*`.
  - Files that fail are left out and listed. Bulk Mark reviewed = `review_documents` (≤ 200 IDs): 07's `review_document` per ID in its own sub-transaction, with skip reasons.

## Cross-cutting rules
- **Privacy:** PAN, mobile, email are personal data (DPDP Act). No PII in URLs, logs or analytics.
- **Cross-firm isolation is tested object by object (18):** `tests/rls/cross-firm/` seeds two firms (A, B) plus an empty firm C on one database and, as Firm A's staff, tries every door into Firm B: each table (read, change B's rows, insert into B, point A's rows at B's objects through every foreign key), each function staff can call (B's IDs and mixed A + B arguments), 10's upload-link functions, Storage and the app's file-link code, and the screens (`tests/e2e/cross-firm.spec.ts`). Every refusal is paired with a **control** (the same call on Firm A's own object must work, or the refusal must name the tenant check), so a case can't pass because of a bad argument; firm-wide figures are asked by Firm C, so any non-zero is another firm's; a snapshot proves Firm B's rows are unchanged afterwards.
  - **Guard:** `public.test_schema_inventory()` (service role only, names and flags, no data) lists tables, views, functions, grants and foreign keys; `guard.test.ts` fails when an object has no line in `tests/rls/cross-firm/coverage.ts` (a case, a `via` to covered objects, or an exemption with a reason), when a table has RLS off, a view isn't `security_invoker`, anything is executable by anon, a Realtime table appears, or Storage gets a policy or a public bucket. **Every new table, view or function adds its line (and its case) in the same PR**, like 08's permission matrix.
  - **Parent checks:** a write policy's `with check (office_id = …)` checks only the row's own firm; a foreign key to a firm-owned parent needs its own check (a trigger's `*_OFFICE` / `PLAN_MISMATCH` error, or an `exists` on the parent under RLS). 18 found one missing (`period.financial_year_id`, fixed: `period_insert` requires the caller's own year).
- **No hard delete;** every mutation writes `activity`.
- **Uploads:** preferred formats per type (11) only ever warn and flag; the allow-list below is the only rule that refuses a file. Allow-list PDF, JPG/JPEG, PNG, HEIC (download-only), XLSX, XLS, CSV, DOCX, ZIP by extension (declared type checked when present); ≤ 25 MB; each extension stored as one canonical MIME type (`src/lib/validation/document.ts` = `private.mime_for_extension` = bucket allow-list); file names sanitised (no separators/control chars/leading dots, ≤ 180). No malware scan or content sniffing in v1 (accepted risk for staff uploads) (03).
  - **Client-link uploads (10, D3):** the same rules, except that **ZIP is refused**. There is no scanner in R1 (accepted risk, revisit after the pilot). A link upload is **download-only until Reviewed**: View is refused in the UI and by `getFileLink` on the server, so an unreviewed client file is never rendered in a staff browser. The caps are 25 MB per file and 30 files / 300 MB per link.
- **Dates:** stored UTC, shown IST; periods follow Indian FY.
- **UI:** the mockup is the UI source of truth — see `references/ui-reference.md` (tokens, components, agreed deviations, screenshots). Each feature spec cites its screens.
- **Accessibility:** WCAG 2.1 AA (wins over pixel fidelity).
- **Errors:** plain user messages; server errors logged with request ID, no PII.
- **Data-access patterns (02):**
  - Multi-row/multi-table writes = **one SECURITY INVOKER SQL function per user action** (atomic, RLS applies, writes one `activity` row). Single-row edits log activity from the server action (best-effort).
  - UI aggregates and PII searches = security-invoker views/functions (e.g. `search_clients`), called from server actions (POST) so search text never reaches a URL.
  - **Search text hand-off (03b):** to carry typed text to the next page (header → `/documents`), use the tab's `sessionStorage`, never the URL. Filters (IDs, enums, dates) may live in the URL.
  - **Limited planner hints (03b):** a function may add an explicit "clients this Limited user can see" filter for speed, but it must mirror the table's SELECT policy exactly (incl. `document_select`'s own-unclassified rule); RLS stays the enforcement.
  - SECURITY DEFINER only for counters/guards, (15) IDs-only lookup helpers whose result is read back under RLS (`private.doc_activity_ids`), and (19) the `public.platform_*` functions, which return firm data (PII in full) to a super admin only after their own caller, firm and window checks, logging every read; every definer trigger checks the tenant (office) first; `search_path = ''` everywhere. Service-role-only helpers live in `public` with EXECUTE revoked (PostgREST can't reach `private`).

## Release & regression policy (every release)
Regression = the **whole** suite (unit, RLS, e2e) — tests accumulate feature by feature and are never edited to pass.
1. **Every PR:** full suite in CI (`ci.yml`): unit; **RLS on an ephemeral local Supabase built only from `supabase/migrations/`** (job `rls`, `scripts/local-db.sh`, chore ci-speed); **e2e on CI's own build against one local stack per shard** (job `e2e`, 3 shards, plus `e2e (all shards)` as one status). They run in parallel and PR CI uses **no secrets and no test lane**. Hosted dev runs the full suite in the nightly Regression and RUN_SLOW dispatches (Regression 110 min, test-lane lease 150 min). Merge only when green. Each PR description carries the AC → test → result table.
2. **Nightly:** `regression.yml` runs the full suite against dev at 01:30 IST; failure emails the owner. Catches drift (settings, paused DB, expired secrets).
3. **Every release (R1, R2 …) — gate before prod:**
   a. `main` green · b. `regression.yml` (manual run) **passes against staging's deployed URL** · c. manual checklist signed off on staging (key screens vs mockup + one real end-to-end path; R1 also the public upload-route security check from 10) · d. owner approval in chat.
   Prod after deploy: **smoke only** (`smoke.spec.ts`: login page, CSP, redirects) — no data-writing tests ever run against prod.
4. **Evidence (kept):** every CI/regression run uploads machine-readable results (JUnit XML + Playwright JSON/HTML) as artifacts (90-day retention). For each release, a record `sdlc/releases/<Rn>.md` is committed with: commit SHA, environment, run URLs, pass/fail/skipped counts per suite, AC coverage, manual checklist results, sign-off (name, date) — plus the result summaries copied to `sdlc/releases/<Rn>/evidence/` so evidence outlives artifact retention.
